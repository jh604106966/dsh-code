# 生产阶段与阶段门（详细版）

配套 `SKILL.md` 的「主流程与阶段门」表：表里给的是判据，这里给每个阶段怎么做、三轨各自交付什么、卡点长什么样。

## 阶段全景

三轨并行推进，每个阶段末对齐一次。

| 阶段 | 玩法轨 | 技术轨 | 质量轨 |
| --- | --- | --- | --- |
| 1. 范围定义 | 核心体验一句话、目标玩家与场景、对标参考 | 引擎与平台可行性初判、技能缺口 | 成败判据、验收方式 |
| 2. 玩法闭环 | 最小闭环、闭环图、试玩记录 | 最小可运行工程、状态与数据流 | 内部试玩观察、困惑点清单 |
| 3. 权威设计 | 规则口径、内容结构 | 定义文件、数据表、扩展路径 | 规则契约断言 |
| 4. 垂直切片 | 一条完整内容的最终质量 | 资源管线、性能优化、构建流程 | 切片缺陷清单、性能基线 |
| 5. 风险探针 | 玩法假设验证 | 技术、平台、性能验证 | 探针结论与复现条件 |
| 6. 自动化自检 | 内容与规则的可测契约 | 检查入口、隔离运行环境 | 断言集、人工检查项 |
| 7. 目标设备验收 | 手感与可玩性确认 | 平台集成、输入映射、生命周期 | 真机记录、性能数据、缺陷单 |
| 8. 数值模拟 | 数值意图与指标定义 | 可无头批量运行 | 模拟器、报告、离群点分析 |
| 9. 存档兼容 | 玩家进度与内容无损 | 读档兼容、迁移逻辑 | 旧档读入测试 |
| 10. 发布收口 | 内容与教学完整 | 构建、签名、渠道接入 | 发布检查表、已知问题清单 |

## 1. 范围定义

**目的**：把「想做的东西」压成可排期、可验收的范围。
**进入条件**：有明确的立项意图或原型冲动。
**完成条件**：一句话核心体验；目标平台与设备；体量上限（内容量、时长、包体、人力、时间）；非目标清单；可验证的成败判据（怎么算做成了）。
**产物**：一页范围书、非目标清单、风险初判表（指向阶段 5）。
**卡点与处理**：范围反复膨胀 → 用「最小可发布体量」倒推，先砍内容量；平台不确定 → 立探针，不要先写平台代码；多方口味冲突 → 用一句话核心体验裁决。

## 2. 玩法闭环

**目的**：证明核心玩法本身成立，而不是被内容量撑住。
**进入条件**：范围已书面确认。
**完成条件**：能连续玩下去不崩；每轮有明确反馈、收益与下一个目标；不看说明就能理解操作与目标；闭环每一步可观察（输入 → 状态变化 → 反馈 → 成长）。
**产物**：可运行的最小闭环、闭环图、内部试玩记录（含困惑点）。
**卡点与处理**：需要额外系统才能撑住乐趣 → 闭环不成立，先改闭环；只做表现没做状态 → 补状态与反馈；玩一次不想再来 → 补成长或变数；把「内容不够」误判成「玩法不好」 → 先看闭环成立性再补内容。
**失败处理**：不加内容，改闭环；两轮改不动则换玩法假设或退回范围定义。

## 3. 权威设计

**目的**：扩内容之前把规则收敛到唯一实现，避免多份真相。
**进入条件**：闭环成立。
**完成条件**：每条规则只有一处权威实现（定义文件或数据）；其余调用点委托过去；文档与实现一致；新增同类内容只改数据；字段有默认值与兼容策略。
**产物**：权威定义（结构 + 字段语义）、数据表、扩展路径说明（新增类型时改哪里）。
**卡点与处理**：同一规则两处实现（例如界面与战斗各算一次伤害）→ 立即收敛；文档与代码漂移 → 以代码为准并补齐文档；加内容必须改流程代码 → 数据驱动没做到位。

## 4. 垂直切片

**目的**：用最终质量标准跑通一条完整内容，暴露真实工作量。
**进入条件**：权威设计可用；资源管线能产出成品级资源。
**完成条件**：一条内容从进入到结算完整体验，使用接近最终的美术、音频、界面与数值；性能与手感接近目标；缺陷清单已知。
**产物**：切片构建、缺口清单、按切片外推的排期与实际工作量对比。
**卡点与处理**：切片用临时资源 → 结论不可信；切片达标但外推排期爆掉 → 这正是切片的价值，按缺口调整范围；切片无限打磨 → 设时间盒，超时按缺口记录并进入下一阶段。

## 5. 风险探针

**目的**：让最大的不确定性在成本最低时变成结论。方法见 [verification-and-risk.md](verification-and-risk.md)。
**进入条件**：识别出高风险未知项（新技术、平台能力、性能上限、玩法是否好玩、第三方服务与审核政策）。
**完成条件**：每个高风险项有明确结论（可行 / 不可行 / 可行但代价是什么）；结论写回设计或范围；探针代码已清理或转为有入口的长期工具。
**产物**：探针结论文档、必要的一次性代码、更新后的范围书。
**卡点与处理**：探针做成半成品主线代码 → 限时限范围，判完即弃；结论只有感觉没有数据 → 记录条件与观测值；结论不利却继续推进 → 改设计或砍功能。

## 6. 自动化自检

**目的**：把「不能坏的东西」变成可重复的机器检查。方法见 [verification-and-risk.md](verification-and-risk.md)。
**进入条件**：有可运行构建；数据与规则契约基本稳定。
**完成条件**：一条命令跑完所有检查；通过 / 失败语义明确；失败可复现、可定位；新增或修复功能同步新增断言；在干净环境可重复运行。
**产物**：检查脚本、运行入口、检查项清单（含无法自动化的人工项）。
**卡点与处理**：为过检放宽或删除断言 → 视为缺陷处理；检查依赖本地残留状态 → 隔离运行目录；检查太慢被人绕过 → 分层，快检查每次跑、慢检查按节点跑。

## 7. 目标设备验收

**目的**：在真实设备与真实条件下确认可玩、可发布。方法见 [verification-and-risk.md](verification-and-risk.md)。
**进入条件**：能在目标设备上安装运行；验收清单已写。
**完成条件**：目标机型、系统版本、输入方式组合上跑通清单；性能、输入映射、生命周期（切后台、来电、锁屏）、权限、存储、网络异常行为均达标并留记录。
**产物**：真机验收记录（设备、版本、结论）、性能数据、缺陷单。
**卡点与处理**：只有模拟器结论 → 不算完成；只看平均帧率 → 看分位与卡顿计数；只在理想网络与满电下测 → 覆盖弱网、低电量、低存储、后台切换。

## 8. 数值模拟

**目的**：批量发现极端值与失衡点，而不是替代手感判断。方法见 [verification-and-risk.md](verification-and-risk.md)。
**进入条件**：数值已数据驱动，可无头批量运行。
**完成条件**：报告可复现（固定随机种子、样本量、参数）、可跨版本对比、离群点被解释或修复、结论与试玩感受方向一致。
**产物**：模拟脚本、报告文件（随代码入库，用于版本对比）。
**卡点与处理**：模拟结果直接写回数据 → 越界，必须人工审阅；只看均值、样本量不足 → 给分布与分位；模拟器与游戏规则不一致 → 模拟器必须调用同一份规则实现。

## 9. 存档兼容

**目的**：老玩家的进度不因结构变更而丢。
**进入条件**：存档格式已定义；存在需要延续的历史存档。只要对外发布过 demo、测试包或抢先体验版本，就按「存在需要延续的历史存档」处理。
**完成条件**：旧版本存档可读；新增字段有默认值；结构变更同步更新权威定义与文档；覆盖缺字段、多字段、损坏档、旧版本号等读档测试。
**产物**：兼容代码、迁移说明、读档测试用例。
**卡点与处理**：只在最新档上测 → 用真实旧档当样本；静默丢档或重置 → 显式迁移或明确告知；只改代码不改文档 → 结构定义文件与文档同步更新。

## 10. 发布收口

**目的**：把构建、资料、风险一次性收干净。模板见 [templates.md](templates.md)。
**进入条件**：内容与数值通过；目标设备验收通过。
**完成条件**：发布检查表全绿，或只剩已记录的非阻塞项；版本号与构建可追溯；商店资料与截图就绪；已知问题清单与回滚方案明确。
**产物**：发布构建（不提交进版本库）、发布检查表、已知问题清单、回滚方案。
**卡点与处理**：把构建产物提交进仓库 → 走发布产物管理流程；带病发布不记录 → 非阻塞项必须写进已知问题清单；发布前才发现平台资料缺失 → 平台资料与功能并行准备；商店页上线、审核与认证周期属时间敏感项，必须倒排进排期，晚动手就来不及。

## 量产（横向扩内容）

切片达标后进入量产。量产不是自由推进的并行活动，照样有闸门。

**进入条件**：垂直切片达标；权威设计可用；自检入口可运行。
**完成条件**：每批内容只改数据不改流程；不产生新分支；断言随内容同步增加；每批内容上线前冒烟通过。
**产物**：内容批次、扩充后的数据表、同步扩充的断言。
**卡点与处理**：某一批开始需要改流程代码 → 停下补数据管线，否则量产会失控；内容越加越久而断言没跟上 → 先补断言再加内容；量产中反复出现规则歧义 → 回到权威设计收敛，不要各自解释。

## 时间盒与倒排

时间盒用于「还不知道要多久」的事，它不是估算结果。

- 时间盒按「能得出一个结论的最小工作量」定；到点必须下结论，允许结论是「不可行」。
- 没有历史数据时宁短勿长：探针以天计，阶段以周或迭代计；超时按失败处理通则降标准或降范围。
- 有外部硬档期时用倒排：先给不可降级项（闭环成立、真机验收、发布前冻结窗口）留位置，再往里塞内容；塞不下就走范围降级阶梯，不压缩验收。
- 倒排时先列出缺失的项目专属值（性能预算、平台资料与审核周期），并把「等这些值才能做」的项单独标出，避免整张排期停摆。

## 阶段门评审怎么开

- 输入：本阶段产物 + 完成条件的证据（命令、版本、设备、结果）。
- 结论只有三种：通过；带条件通过（列出待办与补齐阶段）；不通过（给出退回的阶段与理由）。
- 没有证据的项按未完成处理，不接受口头结论。
- 评审结论要落到文档或任务系统，不要只留在对话里。记录格式见 [templates.md](templates.md) 的「阶段门评审记录」，三轨对齐的结论写进同一份记录。
- 评审结论只有三种写法（通过／带条件通过／不通过）；带条件通过的每一项都要有补齐阶段与负责人，否则视同不通过。

## 范围降级阶梯

砍不动进度时按这个顺序降：

1. 降表现：美术精度、动画、特效、音频。
2. 降内容量：关卡数、角色与物种数、剧情量。
3. 降平台：先出一个平台，其余延后。
4. 降系统：砍次要系统，不砍核心闭环。
5. 降档期。

闭环、可运行性、验收真实性不在降级范围内。

## 节奏与工具处置

- 每个阶段都要有能演示的东西；看不到能玩的东西是节奏失控的信号。
- 长期保留的工具（自检脚本、模拟器、探针界面）要有明确入口与文档，并被设计文档引用。
- 临时脚本只有两种归宿：转为长期工具，或删除。不以「以后可能用得上」长期堆积。
